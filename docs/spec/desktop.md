# @rp/desktop — Electron application

Depends on: every package. Built with electron-vite 5 (three entries: `src/main`, `src/preload`, `src/renderer`). React 19, TypeScript. No UI library (hand-written CSS with CSS variables; light/dark via `prefers-color-scheme` and the `theme` setting). No native modules.

## Main process (`src/main/`)

- `index.ts`: app lifecycle; single instance lock; creates `MainWindow`; registers `rp-asset://` protocol (`protocol.handle`) that serves files **only** from installed pack roots (look up pack root via engine.packs; resolve with `@rp/pack` `resolveAssetPath`; correct `Content-Type`; support `Range` requests for video/audio — implement a range-aware response using `fs.createReadStream` → `Response` with `206`).
- `engine.ts`: builds `Engine` with `FileStorage(app.getPath('userData')/data)`, `packsDir`, `createStandardRegistry()`, `QuickJsRunner`, `createProvider`, host handlers below, a `permissionPrompter` that opens a prompt window for the request and awaits `permissions:respond`, `appVersion`.
- Unprompted messages: `[self-wake]` system notes (what `sdk.llm.wake` hands the model) are hidden in the chat view and timer-origin replies carry no badge, so a wake reads as the character speaking first; the main process shows a desktop notification titled with the character's name (turn replies once the turn finishes, behaviour `chat.emote` messages when added) unless the user is watching that very conversation — the renderer reports it with `app.setVisibleSession(sessionId | null)` whenever the route or active session changes, so a message arriving while Settings is open is announced even though the window is focused. Clicking the notification brings the window back and opens that session (`app:showSession` → `app.onShowSession`). The turn itself never depends on any of this: the engine runs wakes, timers and events whatever the app is showing.
- Session state: `sessions.resetState(sessionId)` (Session settings → *Reset session state*, confirm) forgets scratch state, timers, subscriptions, summary and status; messages stay. Characters have one chat each: the sidebar › and pack card *Chat* buttons open the existing session.
- History editing: `sessions.removeMessage(sessionId, messageId)` and `sessions.clearMessages(sessionId)` (both abort a running turn first and emit `message-removed` / `messages-cleared` chat events; the session, its state, timers and memories stay). Chat header: **Clear history** (confirm); each message shows a delete button on hover.
- Retry: `chat.retry(sessionId)` aborts a running turn, deletes the run of assistant messages at the end of the transcript (`trailingReply`) and runs the turn again over what is left, so the character answers the same user message or `[self-wake]` note afresh. With no reply to drop (the turn errored) it just runs the turn. It refuses (`INVALID_ARGUMENT`) when the transcript is all assistant messages — a session showing only its greeting has nothing to answer. Side effects of the discarded reply (media, memories, timers) are not undone. In the UI: a `↻` next to the newest reply's delete button, and a **Try again** button in the error callout.
- Tray (`index.ts` `createTray`): created on every launch (not only `--hidden`); menu Show / Hide / Check for updates / Quit; click toggles the window. `settings.closeToTray` (default true) makes the main window's close hide it instead (`installCloseToTray`; the `quitting` flag set by Quit/before-quit lets it close); without a tray (no StatusNotifier host / appindicator library) closing quits as before. Linux needs `libayatana-appindicator3` (deb dependency).
- `ipc.ts`: implements every `IpcApi` method as `ipcMain.handle('<ns>:<method>', …)`; forwards `engine.events` `chat` → `webContents.send('chat:event', ev)` to the main window; validates `sender` (only our windows). `browser.*`: `status`, `setPort` (saves the setting and rebinds the loopback server), `trust`/`untrust` (settings + live connection), `installPolicy`/`removePolicy` (`SystemIntegration.installBrowserPolicy` / `removeBrowserPolicy` run `install.sh --browser-only … --user <name>` / `--remove-browser-policy --user <name>` with pkexec, so the policy file is this user's alone; repeatable `--browser-policy-dir <dir>` from `settings.browser.extraPolicyDirs`), `extensionDir`, `blocks` / `clearBlocks` (`rules.list` / `rules.clear` on the connected extension); bridge status changes are pushed on `browser:status`. There is no `setHomePage` here: the home page is a character's to set (`sdk.browser.setHomePage`).
- `capabilities/media.ts`: `CapabilityHandler` for `media`: manages `MediaWindow` instances (one frameless, transparent, `alwaysOnTop` per settings, positioned per `MediaPosition` on the primary display's work area; reuse one window per position; audio uses a hidden window). Sends `MediaCommand` over IPC with `assetUrl(packId, path)`; tracks `MediaItem`s; `close`, `closeAll`, `list`; auto-close on `ended`/`durationMs`; window close → item removed. Per-kind concurrency caps and queues from `settings.media`: see "Media limits and the queue" below.
- `capabilities/video-compat.ts`: before a video item opens, `VideoCompat.playable(file)` decides whether the page can decode it and converts the ones it cannot. The containers a pack may ship (`mp4 webm mkv mov m4v`) hold more than Chromium decodes — H.264/VP8/VP9/AV1 with AAC, MP3, Opus, Vorbis, FLAC or plain PCM — and `.mov` is where that shows: a phone records HEVC, an editor exports ProRes, and the overlay is a dead black window. A file is probed once with `ffprobe` (never a `webm`: nothing unplayable fits in one), and when `conversionPlan` says so, `ffmpeg` writes an MP4 into `<userData>/video-cache`, served under `app.rpchat.video` (`VIDEO_CACHE_PACK_ID`, registered like the TTS and voice-preview roots) — copying the streams that are already fine, so only the picture that needs it goes through H.264, and HEVC on macOS is left alone because the system decodes it. Entries are keyed by the source's path, size and mtime (a video edited in place is converted again), conversions of one file are shared rather than raced, and the cache is pruned oldest-first past `VIDEO_CACHE_MAX_BYTES`. Without `ffmpeg`/`ffprobe` installed, or when a conversion fails, the original is handed to the page exactly as before, with the reason in the log: a missing converter must never stop the videos that do play.
- `capabilities/ui.ts`: `notify` via `Notification`, with an urgency the character chooses (`sdk.ui.notify(title, body, { urgency })`: `low` silent, `normal` the default, `critical` `timeoutType: 'never'`; anything unknown is `normal`); `confirm`/`choose`/`ask` → a prompt window per question (see *Prompt windows* below).
- `loopback.ts`: the `LoopbackServer` on `127.0.0.1` is always started. It binds `settings.browser.bridgePort` (default 47821; env `RP_BROWSER_BRIDGE_PORT` overrides it for tests) and falls back to an ephemeral port with a logged warning when that is taken (`listeningPort`, `requestedPort`, `portFallback`; `rebind(port)` for the settings change). Besides the token-guarded media pages and assets it serves token-less routes registered with `route(prefix, handler)` and hands WebSocket upgrades to `onUpgrade` handlers.
- `browser/` (docs/browser-extension.md): `extension.ts` (`ExtensionService`: locates `resources/extension`, owns `<userData>/extension-key.pem`, packs the CRX once per manifest version, serves `GET /extension/update.xml` (Omaha), `/extension/rpchat.crx`, `/extension/id`), `crx.ts` (hand-written CRX3 + protobuf, deterministic `fflate` zip, Chrome-style id derivation), `policy.ts` (pure: the Chromium policy JSON — force-install and port, nothing else —, the update XML, the Linux policy directories and the per-user policy file name `browserPolicyFilename(user, uid)`) and `bridge.ts` (`BrowserBridge`: accepts `/bridge` upgrades only from `chrome-extension://<id>` origins, waits 5 s for `hello`, asks the user once per id through `uiPrompts` (a `confirm` prompt window; smoke mode auto-trusts), remembers ids in `settings.browser.trustedExtensionIds`, keeps one live connection per id (newest wins), `request(op, args)` with a 15 s timeout, `onEvent`, `onStatus`, `status()`). `tab-updated` events with `status: 'complete'` are pushed into the senses provider as the `browser-navigated` host event. The `browser` capability handler routes every method but `open` through the bridge and applies `settings.web.allowlist` to every URL it opens, navigates to, bookmarks, redirects to or sets as home page. The 2.1 methods (`block/unblock/blocks/clearBlocks`, `imageEffect/clearImageEffects`, `setHomePage/homePage`, `bookmarks/searchBookmarks/addBookmark/removeBookmark`, `eval`, `history/historyVisits/recentHistory`) read `settings.browser` for the toggles (`allowBlocking`, `allowEval`, `allowHistory` → `CAPABILITY_FAILED` naming Settings → Browser), refuse denylist block patterns for 127.0.0.1/localhost/browser schemes (`block` also takes `{ allow }` — the patterns become the only pages that may open, as one catch-all DNR rule the allowed patterns and the app's own hosts override; still `main_frame` only, so an allowed page's assets load freely; a new allowlist lifts the one in place and names it as `replacedAllowlist`), name the acting character on the extension's blocked page, resolve `replaceWith` pack assets to the loopback asset URL (`loopback.rewriteAssetUrl(assetUrl(pack, asset))`), and stretch the bridge request timeout for `eval`. The engine pushes `settings.browser.homePage` to the extension (`home.set`) whenever one connects.
- `capabilities/system.ts`: `openExternal` (http/https only via `shell.openExternal`), `exec` (`child_process.spawn`, no shell, timeout default 30 s, output capped 64 KiB), `readFile`/`writeFile` (absolute path required; cap 1 MiB), `clipboardWrite`. All permission gating is done by core's dispatcher (level `prompt`); these handlers just execute.
- `windows.ts`: `createMainWindow`, `openPromptWindow(payload)` / `closePromptWindow(id)`, `createMediaWindow(position)`; `webPreferences: { preload, contextIsolation: true, sandbox: true, nodeIntegration: false }`; CSP header via `session.defaultSession.webRequest.onHeadersReceived` (`default-src 'self' rp-asset:; media-src rp-asset:; img-src rp-asset: data:; style-src 'self' 'unsafe-inline'`).
- `dev-mode`: if env `RP_MOCK_LLM=1`, `providerFactory` returns a `MockProvider` that answers with a scripted `run_action` showing an image then text, so the app can be exercised without an API key. With `RP_SMOKE_BROWSER=1` on top of `RP_SMOKE=1` the run instead executes `runBrowserSmoke`: it serves `/smoke/page.html` and `/smoke/page2.html` on the loopback server, logs `[smoke] browser bridge listening on port N` (the smoke script launches Chromium with the unpacked extension on that port), waits for the extension, installs a generated pack and sends `browse <url>`, which the mock model answers with a turn exercising `sdk.browser` (status, openTab, read, query, find, type, scroll, screenshot, click, tabs) plus an `sdk.events.on('browser-navigated')` handler; `[smoke] verify browser: PASS|FAIL` reports it. A second message, `exercise <smoke url> <blocked url> <home url>`, runs the 2.1/2.2 capabilities (block `smoke.test/smoke/page2*` and open it — the launcher maps `smoke.test` onto 127.0.0.1 —, unblock, an allowlist of a host that does not exist (the `smoke.test` page is shut out, the app's own 127.0.0.1 page opens unlisted and still loads a `smoke.test` image, a second allowlist naming `smoke.test` replaces it rather than joining it, lifting that one leaves the page open), `grayscale` + pack-asset `replaceWith` read back through `eval`, `setHomePage` (the launcher then opens `chrome://newtab`; the app waits for the `browser-navigated` event on `/smoke/home.html`), add/search/list/remove a bookmark, `eval` in both worlds, history); `[smoke] verify browser capabilities: PASS|FAIL` lists each, and `[smoke] browser smoke done` ends the run. Under `RP_SMOKE=1` a second turn (the message "ask me something") runs `sdk.ui.confirm`, and `verifyPromptWindow` waits for the prompt window to be on screen, screenshots it, clicks *Yes* in it and checks the answer reached the action (`[smoke] verify prompt: PASS`). It runs **after** `captureWindows`: the first turn's image closes itself 20 s after it is shown, so the media checks must not wait behind it. `[smoke] smoke done` marks the end of the run — both smoke scripts grab the framebuffer on `screenshots done` and only then wait for it. None of it happens on a machine whose policy says `dev.allow: false`: `dev-guard.ts` deletes every variable named here from the environment before this module is reached (docs/spec/system.md, "Policy `dev` block").
- `updates/service.ts`: `UpdateService` around `electron-updater`'s `autoUpdater` (injected as `UpdaterLike`, so tests use a fake emitter). Feed: the public GitHub releases of this repository (`build.publish` in `package.json` makes electron-builder emit `latest-linux.yml`; the release workflow attaches it), read anonymously — no credentials are stored or needed. Packaging detection: `APPIMAGE` env → `appimage` (in-place install only when the file and its directory are writable), `execPath` under `/opt` or `/usr` → `deb` (check and notify only; the UI links to the release page), `!app.isPackaged` → `dev` (state `unsupported`, updater untouched). `start()` runs the first check ~30 s after the window is ready and then every `settings.updates.checkIntervalHours` while `settings.updates.automatic` is on and the policy has not set `updates.enabled: false`; `check()` is always allowed manually; `download()` / `install()` (`quitAndInstall(false, true)`) are explicit; `autoDownload` = automatic ∧ can install in place; `autoInstallOnAppQuit` is on. Status transitions (`UpdateStatus` in `@rp/shared/updates`) are pushed on `updates:status`; `index.ts` shows a native "Restart now / Later" dialog when the update is downloaded and the window is visible, otherwise a notification (tray mode), and the tray menu has "Check for updates…".

## Preload (`src/preload/index.ts`)

Builds the `IpcApi` object generically: for each namespace/method a `ipcRenderer.invoke('<ns>:<method>', ...args)`; the `on*` subscriptions use `ipcRenderer.on(channel, (_, payload) => listener(payload))` returning an unsubscribe. Expose with `contextBridge.exposeInMainWorld('rp', api)`.

Three HTML entries: `index.html` (main UI), `media.html` (media overlay) and `prompt.html` (one pending question); a page picks by `window.rp.app.windowKind()` or by entry.

Closing the main window no longer cancels questions that have a window of their own.

Media window: full-viewport React page listening to `media.onCommand`; renders items (image with caption + fade; `<video>`/`<audio>` with autoplay, volume, loop; reports `ended`/`error` via `media.report`); `close`/`close-all` remove items; when no items remain the page reports `closed` for each and main hides the window. Click on an image closes it.

### Code boxes (`components/common/CodeEditor.tsx`)

Every box in the app that holds code is this component: the Sandbox script and its JSON input,
a library function (Pack editor → Scripts), each behaviour hook (Pack editor → Character), and
the two policy JSON boxes under Settings → System. It is Monaco, configured once in
`lib/monaco.ts`:

- **The typings are the character's own.** `capabilities.typings()` — the generated `sdk.d.ts`
  the model is shown and the SDK reference tab prints — is loaded as an extra lib, so completion,
  hovers and errors describe the modules *this* install has, plugins included, and follow the
  registry when it changes. `input` is declared alongside it (the host binds it, so no generated
  typing mentions it).
- **The code is a fragment.** A script is the body of an async function and a library file is one
  function expression, so `return` outside a function and top-level `await` are not reported, and
  suggestion diagnostics are off (the value a top-level `return` uses reads as unused).
  `moduleDetection: force` makes every box its own module, so two hooks may both declare `const
  session` without either being a redeclaration.
- **Workers.** The language services run in web workers and the renderer is a `file://` page:
  Chromium refuses a `blob:`/`data:` worker under the app's CSP (`script-src 'self'`) but accepts
  a sibling `file://` script, which is what Vite's `?worker` import emits. Monaco and those
  workers are several megabytes, so the whole module is behind an `import()` and nothing is
  fetched until a code box is on screen. If that import fails the component falls back to the
  plain `textarea` these boxes used to be.
- The headful smoke run proves all of this in the built app: `verifyCodeEditor` (dev-mode.ts)
  opens the Sandbox tab and asks Monaco's TypeScript worker what follows `sdk.`, which only
  answers if the chunk loaded, the worker started and the typings arrived.

### Media limits and the queue

`settings.media` (`AppSettings.media`, pinnable per key by the policy's `settings.media` block) caps
how many `sdk.media` items may run at once, counted **per `MediaKind`**: `maxConcurrent.{image,video,audio}`
with `0` meaning no cap (the default, so nothing queues unless someone asked for a limit), and
`maxQueued.{image,video,audio}` for how many further calls may wait behind the cap.

`MediaManager` admits every `showImage`/`playVideo`/`playAudio`/`overlay` call through `admit()`:

- Under the cap (and nothing of that kind already waiting) → it starts now and the call resolves
  with a handle whose `state` is `open`, exactly as before.
- At the cap, with room in the queue → the call **does not block and does not fail**. The item joins
  that kind's queue and resolves straight away with `state: 'queued'`. Asking for three videos
  where one may play gets three handles back; the second starts when the first closes, the third
  when the second does.
- At the cap with the queue full as well → `CAPABILITY_FAILED`, naming both numbers.

Queued items are drained by `pump(kind)`, called from `remove()` (a slot just came free) and after
every start (so a raised limit is noticed without waiting for a close). A queued item that starts
raises the `media-started` host event; one that fails to start is reported as `media-closed` with
`reason: 'error'`, since nobody is holding its promise any more. `close()` on a queued handle takes
it out of the queue and reports `media-closed`; `update()` folds its patch into the options the item
will open with; `list()`/`items_()` return open items first, then queued ones.

Admission decisions are serialised (`serialise()`) and count the slots handed to a start that is
still awaiting the backend (`starting`), so two calls racing cannot both take the last slot. The
queue is FIFO per kind — a call joins a non-empty queue even when a slot looks free, so items always
open in the order the character asked for them. The asset is resolved in the entry point rather than
in `start`, so a bad path still fails the character's own call rather than a start it can no longer
catch.

## Packaging

`electron-builder` config in `package.json` (`build` key) for win (nsis), mac (dmg), linux (AppImage, deb). `build.publish` points at the public GitHub repository (`0xbeef1eaf/RPChat`) so `latest-linux.yml` is generated next to the AppImage; the release workflow still runs with `--publish never` and attaches the manifest itself. `pnpm build` must succeed in CI without signing. Do not run electron-builder in tests.
