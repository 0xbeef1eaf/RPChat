# @rp/core — Chat engine

Depends on: `@rp/shared`, `@rp/sdk`, `@rp/pack`, `@rp/llm`. Uses `CodeRunner` as an injected interface (tests use `FakeRunner`). Node only (fs for storage).

## Services

**PackService**: `install(sourcePath)` (dir or .rppack → copies/extracts into `<dataDir>/packs/<id>/<version>/`, writes `InstalledPackRecord`; if same id already installed: replace; then runs the character's `onInstall` behaviour right away, once — permissions are app-wide, so nothing is ever pending; the loader's warnings, e.g. an ignored legacy `capabilities` key, are logged), `uninstall(id)` (removes files, record, timers, and sessions' ability to continue: sessions remain but `send` fails with NOT_FOUND), `inspect(sourcePath)` (`PackInspection`: manifest, characters, README, asset counts/tags — no permission information, since packs carry none), `list()`, `getLoaded(packId): LoadedPack` (cached; a pack has exactly one character, `pack.character`), `characters(): CharacterSummary[]` (one per installed pack), `exportPack(id, dest)`. The character's function library is part of the loaded pack (`LoadedCharacter.library`, bundled by the loader) and changes only with the pack. `onPacksChanged(listener)` reports every install, replacement and uninstall as `(packId, previous?)` — `previous` being the `LoadedPack` that was loaded until now, absent for a pack this app had not loaded; the Engine uses it to recompute event interest, drop the library prelude cache and run `followPackUpdate` (below).
Pack installation directory root is `EngineOptions.storage`-adjacent: pass `dataDir` via `FileStorage` (expose `storage.dataDir`) — or accept `packsDir` in EngineOptions; choose `packsDir: string` in EngineOptions.

**PermissionService**: permissions are **app-wide and per function**; the only control is `settings.permissions.functionAllow` (Settings → Permissions), applied to every installed character alike. Its keys are a module id (`avatar`) or one function (`avatar.show`), a function entry wins over its module's, and an unmentioned key is allowed — so a function a later version or a plugin adds arrives switched on. `sdk.lib` is not a module, is always available and never listed, and a stored `lib` key is ignored (`ALWAYS_AVAILABLE_MODULES` in `@rp/shared/permissions.ts`; the helpers `functionAllowed`, `moduleAllowState`, `selectionCovers`, `mergeLegacyModuleAllow` live there too). Packs neither request nor are granted anything, and there is no grant store. `effective(packId?)` → `{ effective, denied }`: `effective` is `AllowedModule[]` (`{ id, methods }`, registry order, modules with nothing left omitted) and `denied` maps each switched-off `module.method` to the (only) `DenialReason` `'policy'`; `allowedFunctions(packId?)` (the same list — the sandbox surface and the prompt's SDK index are built from it), `allowedModules`, `deniedFunctions`, `deniedModules` (only modules with no function left), `denialReason` (`DENIAL_TEXT.policy`: "switched off under Settings → Permissions"), `policyAllows(settings, module, method)`. `isAllowed(context, module, method): Promise<'allow' | 'deny' | 'prompt'>` (`lib` → allow; switched off → deny; trusted/pack → allow; prompt → allow when a session-scoped remembered decision exists, else prompt), `prompt(request)` → uses `permissionPrompter`, stores `allow-session` decisions in memory keyed by sessionId+module+method; `clearSession(sessionId)`. The `packId` parameters remain for call-site compatibility only.

Two module-level helpers in the same file shape what the character is *told*: `selectionOptions(allowed)` turns an `AllowedModule[]` into the `{ modules, methods }` pair the `@rp/sdk` generators take, and `promptSelection(allowed, promptFunctions)` narrows it to the character's own `character.json` selection (absent = everything allowed, `[]` = nothing but `sdk.lib`). `ChatService` builds the prompt from `promptSelection(...)` and `BehaviourService.surfaceFor` builds the sandbox surface from `allowedFunctions(...)` alone: the pack's narrowing never changes what the code may call. `HelpHandler` follows the prompt selection, since `sdk.help` is the prompt's own continuation; `module(id)` adds `unavailable: string[]` naming the functions its typings still describe but the character may not call.

A settings patch **replaces** `functionAllow` rather than merging into it (so a key can be taken back out); `mergeSettings` folds a stored `moduleAllow` from a pre-function build into it, module keys meaning what they always did.

**CapabilityDispatcher** (`invoke(call)`): resolve handler by module (core-provided or host), check registry knows module/method (CAPABILITY_UNKNOWN), permission check (PERMISSION_DENIED / PERMISSION_PROMPT_REJECTED), invoke, wrap errors, append `AuditEntry` (allowed/denied/failed with durationMs), return `CapabilityResult`. Values must be JSON: run the result through `JSON.parse(JSON.stringify())`, `undefined` → `null`. It also implements `recordLibCall(LibCall)`, the other half of `CapabilityInvoker`: the sandbox reports each settled `lib.<name>(...)` (docs/spec/sandbox.md §3) and the dispatcher appends it as an `AuditEntry` with `module: 'lib'` and the function's name as the method, so the action log holds the library calls beside the sdk calls the same run made. There is nothing to check — the function has already run inside the isolate — so the write is not awaited and nothing is returned.

**Core-provided handlers** (`src/handlers/`): 
- `chat`: `say`/`emote` append an assistant `ChatMessage` (origin from context.trigger, kind emote) and emit `message-added`; `history`; `setStatus` emits `status`.
- `state`: scopes `char:<packId>/<charId>` and `session:<sessionId>`; values capped at 32 KiB each, 200 keys per scope.
- `pack`: uses `@rp/pack` `resolveAssetPath` + asset index; `readText` limited to text kind.
- `timers`: `schedule` persists `ScheduledTimer` + arms `setTimeout` (re-armed on `start()`, overdue timers fire immediately, ≤ 20 per session); on fire: if the character has `onTimer` behaviour run it with `{ timer }` else inject a system-origin user message `"[timer fired] label/payload JSON"` and run an LLM turn. Provide `cancel`, `list`.

**LibraryService** (`services/library.ts`): the character's function library — the `lib` global, which the sandbox also exposes as `sdk.lib` (docs/spec/sandbox.md §3, §5: `sdk.lib === lib`, so `sdk.lib.<name>(...)` is a library function, not a capability call). The library is the TypeScript the author ships in `characters/<id>/lib/` (docs/spec/pack.md "Function library"), bundled by the pack loader into `LoadedCharacter.library: CharacterLibrary`; nothing at run time adds to it or takes from it, and there is no `lib` capability module (the engine refuses a plugin registering the id `lib`). The service is constructed with `LibraryPacks` (`PackService.getLoaded`) and has three members: `functions(target)` (every `LibFunction { name, file, params, description?, internal? }`, internal ones included — the prompt filters them), `preludeFor(packId, characterId)` and `invalidate(target?)`. An uninstalled pack, or a character it lacks, has no library. `buildPrelude(library)` renders `const lib = __rp_lib(<library.code>, ["<internal name>", …]);` (the second argument only when there are internal names; `EMPTY_PRELUDE` = `const lib = __rp_lib({});` when `code` is empty, i.e. no library or one that does not build), `__rp_lib` being the sandbox bootstrap's factory that wraps each function and makes the object `sdk.lib`. `preludeFor` caches it per character; the Engine calls `invalidate()` on every pack change. The prelude reaches every run as `CodeRunRequest.prelude`: `ChatService.runLlmTurn` sets `TurnInput.prelude` for `ActionLoop.runAction`, and `BehaviourRunner` (`run`/`runScript`: timer code, event handlers, lifecycle hooks) asks its `prelude` option. `ChatService` also removes `LIB_STATE_KEY` (`lib.functions`, where very old versions kept saved functions; nothing reads it) from the `<state>` block.

**Internal helpers.** A library export whose JSDoc carries `@internal` (docs/spec/pack.md "Function library") is the author's plumbing, not the character's — typically something a sibling file imports. It means exactly two things: the model is not told about it, and the model's own code cannot call it. `PromptBuilder` leaves it out of `<library>` (`functions` still returns it).

The prelude itself is the same for every run: one `lib` carrying every export, with the internal names as `__rp_lib`'s second argument.

```js
const lib = __rp_lib((() => { /* the bundled lib/ folder */ return __rp_library; })(), ["<helper>"]);
```

The sandbox enforces the rest (docs/spec/sandbox.md §3): in a run whose `trigger.kind` is `llm` an internal function throws when the action body calls it, and goes through when another library function does. Every other trigger — the pack's behaviour hooks, event handlers, `code` timers, the Sandbox tab — calls it normally, so `BehaviourRunner.runFor` and `runScript` ask for the same prelude.

There is deliberately no second scope. A nested `lib` shadowing an outer one is renamed by the transpiler (`lib` → `lib2`), and a handler a library function hands to `sdk.events.on` / `sdk.timers.runLater` is stored as its *compiled* source (§4) — so the rename used to travel into the stored code and fail there with `ReferenceError: 'lib2' is not defined` the moment the event fired. This is a visibility boundary, not a sandbox one: every one of these functions is the character's own code running with the same permissions, and a library file that imports a sibling's export calls it directly, past the `lib` object.

**Following a pack update** (`services/pack-update.ts`, `followPackUpdate(deps, packId, previous?)`, wired to `PackService.onPacksChanged`): what a pack says about its character — persona, behaviours, library, avatar, voice — is read from the loaded pack on every turn, so an install over a running app reaches the open conversation by itself. What does not is the session record, and that is this module: a pack has exactly one character, so when the update renamed the character id the session's `characterRef` follows it (otherwise the chat would be dead: `getCharacter` throws `NOT_FOUND` for the id the session remembers), and with it everything keyed by that ref — the `char:<ref>` state scope (mood and routine included), the memories and their cached vectors, pending timers and event subscriptions; a key that already exists under the new ref wins, since the new pack shipped it. The title `SessionService.create` generated (`autoSessionTitle`: `<character> (<pack>)`) is re-rendered from the new names when it still matches what `previous` would have produced — a title the user typed is left alone, as is every title when `previous` is absent. A session is written (and its `updatedAt` moved) only when something about it actually changed, and an uninstall changes nothing: the pack is no longer loaded, so the module returns at once and the session keeps waiting for the pack to come back.

**SessionService**: one session per character — `create` returns the character's existing session (newest by `updatedAt`) instead of a second one, so no second greeting or `onSessionStart`; `forCharacter(ref)` looks it up. `resetState(sessionId)` clears the `session:<id>` state scope (sandbox scratch, history summary, autonomy counters, consolidation marker), pending timers, session permission allows and, through the after-reset hook, event subscriptions; it emits `status: null` and `session-reset`. `ChatService.resetState` aborts a running turn first. Messages are untouched.

**SandboxService** (`services/sandbox.ts`, `engine.sandbox`): ad-hoc scripts the user runs by hand from the desktop app's Sandbox tab (`IpcApi.sandbox`). `run({ packId, characterId, code, input?, runId? })` validates the request (`SANDBOX_CODE_MAX` 64 KiB, `runId` `[A-Za-z0-9_-]{1,80}`, `input` JSON-serialisable), rejects `NOT_FOUND` for an unknown pack/character, takes the character's session (`SessionService.forCharacter`, `create` when it has none — which runs the greeting and `onSessionStart` like any first chat) and calls `BehaviourRunner.runScript` with the trigger `{ kind: 'sandbox', runId }` inside `ChatService.runExclusive`, so a run waits for a turn in progress and nothing else touches the session meanwhile. The script is therefore exactly a behaviour/action body: `wrapBehaviourScript` binds `const input = <json>;` on the first line (`null` when omitted), the character's library prelude defines `lib`, the surface is the pack's allowed modules, limits come from `settings.runLimits`, and `sdk.chat`, memories, state and timers land in the character's session. It resolves with `{ runId, sessionId, result: CodeRunResult }` — a failed script is an `ok: false` result, never a rejection; only a bad request, a missing character or a host failure reject. `cancel(runId)` aborts the run through its `AbortSignal` (true when it was still going; the runner reports `SANDBOX_TIMEOUT` with `termination: 'aborted'`); `active()` lists running ids; `cancelAll()` aborts them all (`Engine.stop` calls it). Every run is recorded in the audit log as `sandbox.run` with args `[runId, codeLength, callCount]` and outcome `allowed`/`failed`, next to the SDK calls it made (those are audited by the dispatcher as usual). `ChatHandler` maps the `sandbox` trigger to message origin `behaviour`.

**Timer delays**: `settings.autonomy.minDelayMs` (default 30 s, hard floor 1 s) is the shortest delay for `timers.schedule`, `timers.runLater` and a delayed `llm.wake`; shorter values are raised to it (`validateDelay`), never rejected, and the engine rules quote the configured value each turn so characters plan in minutes. `llm.wake` without `delayMs` still runs right after the action.

**PromptBuilder**: implements ARCHITECTURE §6. Sections wrapped in `<engine_rules>`, `<persona>`, `<sdk_reference>`, `<library>` (only when `PromptInput.library` is non-empty: a heading line "Your own functions (call them as lib.<name>(...) or sdk.lib.<name>(...), the same object):" then one line per non-internal function `- lib.<name>(<params>) — <description>`, params and description being `LibFunction.params` / `.description` as the loader read them (the declaration's parameter list, the JSDoc summary); it is dynamic, so it opens the non-cached tail right after `<sdk_reference>`), `<history_summary>` (only when a summary covers part of the transcript), `<memory>`, `<session>` tags. The engine rules add: "The functions under <library>, when there is one, are yours to call as lib.<name>(...) in any action, timer or event handler; prefer them over re-writing the same steps. sdk.lib is that same lib object, so sdk.lib.<name>(...) works too. The library is fixed: there is no lib.register or sdk.lib.define." `<sdk_reference>` is the `generateSdkIndex` output: every available module's methods with signature, full TSDoc summary, parameters, returns and first example, straight from the typings; functions switched off under Settings → Permissions are not mentioned at all, and neither are the ones the character's `promptFunctions` leaves out (the `help` module serves complete typings/docs per module on demand, filtered the same way). `build()` also returns `stats` (system/sdk-reference token estimates, transcript budget, dropped messages, summarised messages and summary tokens, messages whose action detail was trimmed); `ChatService` logs a warning when the system prompt exceeds half of `contextTokenBudget` or messages were dropped.  There is no pack/asset listing: the engine rules direct the character to `sdk.pack.tags()` / `findAssets` / `listAssets` (the abridged SDK index already names the available modules). The rules push the character towards acting rather than describing action — reach for the sdk when doing beats saying, never mime a capability it has (no `*shows you the photo*` without `sdk.media.showImage`), balanced by the restraint rules (one action per intention, short code, nothing the moment does not call for). State JSON capped at 4 KiB. When `useToolCalling` is false or the provider lacks tools, engine rules explain the ```action fence instead of the tool. Transcript → `LlmMessage[]`: user/assistant text; assistant messages with actions expand to assistant(text + tool_use parts) + user(tool_result parts) pairs (or, in fenced mode, assistant text containing the fence + user `<action_result>` JSON). System-origin messages (timer wake-ups) become user messages prefixed with `[system]`. Apply `windowMessages` with `contextTokenBudget` (default 64k) minus the system prompt estimate.

**HistoryService** (`settings.history`): keeps a long session inside the context window without deleting anything. Two independent mechanisms, both prompt-only — storage and the chat view always hold every message with its actions.

- *Background summarisation.* After a turn, `ChatService.afterTurn` calls `shouldCompress` (transcript token estimate, counting action code and results only for the messages `keepActionDetailFor` will actually send) and, above the threshold, kicks off `compress()` off the turn. The threshold is `compressAboveTokens` when the user pinned one and otherwise derived — `COMPRESS_BUDGET_FRACTION` of the room the last prompt of that session measured for its transcript (`PromptStats.transcriptBudgetTokens`), so it follows the context budget and the model instead of being an absolute that means something different on every one. A turn whose window had to drop messages (`PromptStats.droppedMessages > 0`) forces a run whatever the threshold says: those messages are covered by neither the summary nor the prompt, so without it they leave the conversation silently. Saved settings still on the earlier fixed default of 6000 are migrated to auto.
  `compress()` summarises everything except the last `keepRecentMessages` messages into a rolling `HistorySummary` (`text`, `segments`, `throughMessageId`, `messageCount`), stored in state under `session:<id>` / `history.summary`. Runs are serialised per session and never throw; a second call while one runs returns the running promise. Each run recaps only the messages added since the previous summary — the earlier summary goes in as read-only context — and **appends** the result as a segment; earlier segments are kept word for word, because re-summarising a summary loses a little every time. Only when the joined segments outgrow `summaryBudgetTokens` is everything but the newest folded into one, in a single extra call (`foldToBudget`); a fold that fails leaves the segments alone for the next pass to retry. `text` is the segments joined and is what the prompt shows; a summary stored before segments existed reads back as one. The transcript handed to the summariser carries a bracketed line per action (purpose, and whether it failed — never the code), so what the character *did* survives compression. `PromptBuilder` drops every message up to `throughMessageId` and emits `<history_summary>` instead; if that message is no longer in the transcript (history cleared, message deleted) the summary is ignored and the transcript is used whole. `ChatService.clearMessages` clears the summary with the messages.
- *Action trimming.* `keepActionDetailFor` (default 0: no past tool calls are re-sent; the in-flight turn always carries its own rounds) keeps the code and results of the N most recent assistant messages that acted; older messages contribute only their visible text. Saved settings still on the earlier default of 2 are migrated to 0. `transcriptToMessages` drops a message's `tool_use` and `tool_result` blocks together, so a result is never orphaned from its call, in both tool and fenced mode.

**ActionLoop** (`runTurn`): 
```
emit turn-started
create assistant message (empty) → emit message-added
budget = maxActionRounds
for round in 0..budget:
  provider.chat(request, { onTextDelta → append to message.content, emit text-delta })
  actions = tool_use parts named run_action (+ fenced blocks from text when in fenced mode or when found anyway)
  if none: break
  for each action (sequential): emit action-started; runner.run(...); attach result; emit action-finished
  append tool_result parts (JSON of { ok, returnValue, error, failedCalls, logs }) to the next request
  if round == budget and a result failed repairably and repairs < maxActionRepairs:
    budget += 1 and append ACTION_REPAIR_NOTICE to those same results
  else if round == budget: append a final user message "[system] action limit reached, reply with text only" and do one last provider.chat without tools
persist message, emit message-updated, turn-finished; on error attach error and emit error
```
Failures as the model gets them (`errorForModel`, `resultPayload`): `code`, `message`, a `fix` line
taken from `FAILURE_GUIDE` — one per `RpErrorCode`, saying how to correct that kind of failure — and,
for its own code, `line`/`column`/`frame`/`stack` in `action.ts` coordinates. An sdk call that failed
and was never caught arrives as `SANDBOX_RUNTIME` carrying the capability's own code under
`details.code`; that inner code is what the `fix` is chosen by. Calls that failed *without* ending the
run (caught, or never awaited) are listed under `failedCalls` — `call: "sdk.<module>.<method>"` plus the
same detail — so a `try/catch` cannot report success where a call failed; the call that did end the run
is left out, it is already the run's `error`. `PromptBuilder` replays a stored result through the same
`resultPayload`, so a replayed failure reads exactly as it did live.

**Repair rounds** (`TurnInput.maxActionRepairs`, `settings.maxActionRepairs`, default 2, `-1`
unlimited): when the round that used up the budget failed in a way `isRepairable` says different code
could get past — its own compile/runtime error, a wrong argument, an unknown method, a path that
escaped, a budget it can split — the loop grants one more round and appends `ACTION_REPAIR_NOTICE`
to that round's results instead of ending the turn, up to the cap. A failure a rewrite cannot fix
(`PERMISSION_DENIED`, `PERMISSION_PROMPT_REJECTED`, `CAPABILITY_FAILED`, …) grants nothing: the
character is told plainly, in the same `fix`, that retrying is not the answer and to tell the user.
The model is never *forced* to act again — a turn that replies with text only after a failure ends
there, as it always did.
Abort: `chat.abort(sessionId)` aborts the provider `signal` and the runner `signal`; partial text is kept and persisted.
Model traffic: with `TurnInput.captureExchanges` (ChatService passes `settings.debug.showModelTraffic`, plus `providerLabel` = the provider config's label or id) every provider call emits exactly one `model-exchange` chat event (`ModelExchange`: kind `turn`, `round` index from 0, the final text-only call after the action limit included, `turnId`, `messageId`, a `structuredClone` snapshot of system/messages/tools taken before the call, then `response` with usage/stop reason or the serialized `error`, and `durationMs`). `sdk.llm.ask` (and screenshot descriptions) emit the same event with kind `llm.ask`, memory extraction with kind `memory`; all three go through `services/exchanges.ts` `recordExchange`. When the setting is off nothing is copied or emitted.
`sdk.chat.emote` during an action appends a separate assistant message *before* the streaming one is finalised; that is fine — order them by createdAt.

**ChatService**: `send(sessionId, text)` → queue the message, then persist it, run `onUserMessage` behaviours (may return `{ skipLlm: true }`) and `ActionLoop.runTurn`. Serialise turns per session (a queue); `send` while a turn runs queues the message for the next one and resolves when that turn is done. `abort(sessionId)`.

The user's queue (`queued(sessionId)`, `unqueue(sessionId, messageId)`, `dropQueue(sessionId)`, the `queue-changed` event). A message that arrives while the character is answering is held in the service — not in the transcript — and the next turn takes the **whole batch**: each message is persisted and put through `onUserMessage` in the order it was sent, then one reply answers them all, rather than one turn per message chasing the last. The reply is skipped only when *every* message in the batch asked for it (`{ skipLlm: true }`), so a pack that scripts some replies itself does not silence the rest. One drain is queued per batch: while it waits its turn it collects the messages that arrive after it, and the first `send` after it has taken its batch queues a fresh drain behind the turn it is running. `send` resolves when the turn that delivered its message finished; `unqueue` (which the composer's × calls) resolves it without a reply, since taking a message back is not a failure. The queue is dropped, undelivered, when the conversation it was meant for goes away — `clearMessages` and a deleted session (`Engine`'s `setAfterRemove`). Stopping a reply does not drop it: Stop ends *this* reply, and what the user has already said is still waiting to be answered.

Two queues, both `KeyedQueue` (`keyed-queue.ts` — the one place the engine's per-key serialisation lives; `FileStorage`, `EventService` and `TimerService` use it too). `turns`, keyed by session, is the conversation: user messages, self-wakes, the LLM turns they run and the edits (retry, reset, clear) that must not race with one. `background`, keyed `<sessionId>\0<trigger>`, is the character's own code: a `code` timer and an `onTimer` behaviour run there, off the turn queue, so a reply in progress does not have to finish first — the way event-subscription handlers have always run (docs/spec/living.md §3.3). `isBusy`/`isRunning` and the Stop button describe turns only; background work is not something the user is waiting on. `idle(sessionId?)` drains both, and `abortBackground(sessionId?)` cuts the background runs short (`Engine.stop` calls it before `timers.stop()`, because a fire waits for its run and a run can sit in a host call for minutes).

`TimerService` serialises fires **per timer** rather than globally: a repeating timer never overlaps itself and is re-armed only when its run is done, while two different timers fire alongside each other. `fireDue()` stays sequential — it is the deterministic test path.

What this gives up is ordering between a background run and a turn. Two runs may interleave their `sdk.state` writes, so a read-modify-write spread across both can lose an update; a single `set` is safe (`FileStorage` keeps one mutable map per scope and serialises the writes to its file), a `get` then `set` in two overlapping runs is not. This is the tradeoff the event handlers already accepted.

**SessionService**: CRUD; `create` writes the greeting as first assistant message (origin greeting) and runs `onSessionStart` behaviours; `remove` deletes messages, session state and timers.

**SettingsService**: `get()`, `update(patch)` with `DEFAULT_SETTINGS` + `DEFAULT_RUN_LIMITS` merge, provider CRUD by array replace, `testProvider`, `listModels`.
